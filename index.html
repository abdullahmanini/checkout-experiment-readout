A/B test readout · synthetic data

Did a one-tap wallet button lift checkout conversion?

I built the pipeline, data tests, metric definitions and analysis for a two-week checkout experiment at a fictional retailer. The first number looked like +4.6 points. A logging bug in two app builds caused most of that, and the real lift is about +2.6.

Larchway Outfitters is fictional, and every customer, payment and dispute comes from a seeded Python model. The study is not affiliated with any payments company or retailer. Because the model simulates every customer under both versions, the true effect is known, so the readout can be checked against it.

01
Plan

The question and the plan, fixed before launch

Larchway's checkout asks for card details on every order. The treatment adds an express wallet button that pays with stored, tokenized details in one tap. Does that raise the share of customers who finish checkout without hurting authorization, refunds or disputes?

UnitCustomer, bucketed by a salted hash of customer_id, so the arm stays the same on every device
Split50/50, all platforms, Canada and the US
AnalyzedCustomers who reach checkout, the first screen where the versions differ
Primary metricCheckout conversion: customers with an order ÷ customers who reached checkout
GuardrailsAuthorization rate (margin 0.5 pp), refund rate (1.0 pp), dispute rate (0.15 pp, re-read at 90 days)
Sample size per arm to detect 1.5 pp from a 66% baseline (α 0.05 two-sided, 80% power)
Duration14 days, two full weekly cycles, no early stop for a good result

The full plan, including the decision rules and the one margin I changed after a first run, is in docs/experiment_plan.md.

02
Pipeline

Three sources, one customer table, fifteen tests

The data arrives the way it would in practice: an assignment log from the bucketing service, client analytics events from the apps and website, and a server-side payments ledger with refunds and disputes. These are separate systems with separate failure modes.

Raw
As landed
  • assignments
  • customers
  • checkout events
  • payment attempts
  • refunds, disputes
Staging
Typed, deduplicated
  • typed columns
  • first copy of each resent event
Marts
Business grain
  • checkout sessions
  • orders
  • one row per customer
Semantic layer
Metrics as code
  • metric definitions
  • compiled SQL
Readout
Statistics
  • SRM, delta method
  • CUPED, Holm

The data tests in sql/tests.sql run after the marts are built. An error stops the pipeline before any analysis. A warning is reported and has to be explained in the readout. Three warnings fired, and two of them led straight to the logging bug.

Row counts and failing rows: docs/test_results.md. Everything runs on Python's standard library and SQLite.

03
Metrics layer

Each metric is defined once and compiled to SQL

Every metric is a ratio of two measures summed over customers, the unit that was randomized. From one definition, semantic_layer.py produces two queries. One returns the metric value for dashboards. The other returns the sums, squares and cross-products the variance formulas need, so the confidence interval and the dashboard number come from the same definition.

Authorization, refund and dispute rates are counted per attempt or per order, but one customer can make several of each. Treating attempts as independent would understate the variance, so those metrics use the delta method on customer-level sums.

What happened

      
iOS 7.2.0 and Android 5.9.0 shipped the same mobile checkout module on Sep 18. In the treatment version, when a customer opened checkout and left without paying, the module often lost its queued analytics events. Payments are recorded on the server, so every buyer was still counted. The treatment group lost mostly non-buyers, which pushed its conversion rate up.

      
The payment-side test (payment_sessions_have_client_event) passed, because the bug only touched sessions that never reached payment. Only the balance check found it.

      
The fix: exclude both builds from both arms. The build is recorded when the customer is bucketed, before checkout is shown, so the exclusion removes the same kind of customer from each arm. After it the split is  to  (p = ). The cost is power:  customers per arm against the planned , so the detectable effect rises from 1.5 to  pp.

Half the customers are new and have no prior spend, and revenue per customer mostly depends on whether someone buys at all. A covariate that exists for everyone, such as prior sessions, is the next thing to try.

    

  






  

    
06
Over time

    

      
Stopping early would have overstated the lift

      
The result crossed p < 0.05 on day 3 and never went back. Had the test stopped on day 4, when p was 0.0001, the reported lift would have been , half again as large as the final figure. Estimates that cross a threshold early tend to be the high ones, which is why the plan fixed the horizon at 14 days.

09
Decision

    

      

        
Recommendation

        
Ship to 95% and keep a 5% card-form holdout until Dec 26.

        
The primary metric rose significantly and the authorization and refund guardrails pass. The plan's rule for an open dispute guardrail is to ship with a holdout and re-read at 90 days.

      

      
    
        
  1. Re-read disputes on Dec 26, 2026, when the test's orders are 90 days old, against the 0.15 pp margin. Track express orders from new customers on their own, since that is where a fraud problem would show first.

  2. Log exposure on the server when checkout renders, so a client bug cannot remove customers from the denominator again.

Limits
